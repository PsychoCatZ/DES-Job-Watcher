# 19. Из SQLite во вход Luna

`examples/analyze_saved.py` связывает историю карточек с уже существующим анализатором. Код читает последнюю сохранённую версию карточки и происхождение результата из `candidates.json`. Источник определяет профиль для анализа; это ещё не заключение о соответствии. Сейчас используются support и ai_data.

`DescriptionParser` наследует стандартный `HTMLParser`: `handle_data` получает текст, а обработчики тегов добавляют границы абзацев и пунктов. Мы сохраняем оригинальный HTML в базе и отдельно создаём текст для анализа. Поэтому преобразование не уничтожает исходник.

`make_api_snapshot()` переводит ответ официального API в формат, который принимает существующий `build_input()`. После этого используются те же профили, правила и контракт. `prepare_body()` проверяет актуальность входа до ввода ключа и сетевого вызова.

Сценарий без `--live` сохраняет подготовленные входы в `data/analysis_batches/<время>/`, печатает вакансии и не обращается к сети. `--vacancy ID` позволяет выбирать карточки явно; аргумент можно повторять. `--limit` ограничивает количество пар вакансия–профиль, а не уникальных вакансий.

При `--live` запрашивается ключ OpenAI со звёздочками. Модель остаётся GPT-6 Luna. Каждый ответ сохраняется отдельно, без изменения исходного текста ответа. Ошибка останавливает партию. Файл `in_flight` перед запросом отмечает незавершённую попытку: прерывание не означает, что провайдер не обработал платный запрос.

Это ограниченный ручной запуск. Между партиями ещё нет автоматического пропуска уже проанализированных пар: перед повторным платным запуском нужно проверить результаты. Нет автоматического ранжирования, фильтра Data Light перед LLM и общего отчёта рекомендаций — эти задачи остаются следующими. Архивные карточки пропускаются. Зарплата и график остаются информацией.

Первые записи поисковой выдачи не обязательно лучшие. Для первой проверки выбираем несколько карточек явно и сопоставляем решение модели с полным текстом, а не оплачиваем весь список без разбора.
