# 17. Официальный HH API и приоритет поиска

Цель Watcher — находить подходящую работу. Основные направления — поддержка и разметка / AI-data. Разработка остаётся дополнительной и включается явно. Уроки сопровождают готовые шаги, разбор можно читать после запуска.

## Что добавлено

`des_job_watcher/hh_api.py` отвечает за HTTP. `examples/collect_hh.py` соединяет настройки, локальный ввод реквизитов, поиск и сохранение отчёта. `config/search_plan.json` задаёт запросы и `default_profiles`. Смена приоритета поиска не меняет факты резюме или критерии оценки.

`with HHClient(...) as client` создаёт одну HTTPX-сессию и закрывает её даже при ошибке. Методы `__enter__` и `__exit__` позволяют нашему объекту работать с конструкцией `with`.

Для первого токена отправляется POST `/token` с `grant_type=client_credentials`, `client_id`, `client_secret`. Аргумент `data=` кодирует поля как форму; это не JSON. Ответ разбирается через `response.json()`. Полученный токен используется только в заголовке `Authorization` следующих запросов. Callback для этой авторизации не требуется.

HH рекомендует получить токен один раз: повторная выдача отзывает предыдущий. Код не получает новый токен автоматически и не повторяет запрос при ошибке. Токен сохраняется только в памяти процесса; для следующего запуска его можно взять в личном кабинете приложения HH. Не передавайте реквизиты через чат или аргументы командной строки.

`getpass()` скрывает ввод. Этот сценарий запускается в обычном интерактивном терминале. Реквизиты не записываются в отчёт или файлы конфигурации.

## Запуск

Без сети, посмотреть план:

```powershell
.\.venv\Scripts\python.exe -m examples.collect_hh
```

Первое получение токена и поиск:

```powershell
.\.venv\Scripts\python.exe -m examples.collect_hh --live --issue-token
```

При наличии токена приложения:

```powershell
.\.venv\Scripts\python.exe -m examples.collect_hh --live
```

Сценарий запрашивает `HH-User-Agent`, например `DES-Job-Watcher/0.1 (ваша контактная почта)`. Затем — готовый токен либо реквизиты приложения. Для отдельного дополнительного поиска используется `--profile developer`.

## Как движутся данные

Настройки → шесть поисковых запросов → словарь по HH ID → JSON и Markdown в `data/hh_api/<время>/`. У одного ID сохраняется несколько источников: вакансия может встретиться в нескольких запросах и профилях. Это происхождение результата, а не вывод о соответствии резюме.

`setdefault(id, ...)` возвращает уже существующую запись или создаёт новую. Поэтому повторное появление ID дополняет `sources`, а не создаёт вторую карточку. Такая дедупликация работает внутри одного запуска; история между запусками потребует SQLite.

Поиск ограничен первой страницей каждого запроса, по 20 элементов. Между запросами — 0,6 секунды, без параллелизма. Это ограничение нагрузки, а не гарантия доступности. Зарплата и график не входят в параметры фильтрации. Список ещё не прошёл проверку работодателя, голоса, полных обязанностей и соответствия резюме — в отчёте это указано явно.

## Проверка

`httpx.MockTransport` подставляет вымышленные ответы вместо сети. Тесты проверяют форму авторизации, передачу токена, отсутствие зарплатных фильтров, сохранение источников при дедупликации и остановку без утечки тела ошибки. Реальная авторизация подтверждается только отдельным запуском с реквизитами владельца.
