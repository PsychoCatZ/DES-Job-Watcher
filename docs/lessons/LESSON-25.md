# 25. ID доказательств и готовность к основной работе

Контракт 4 и инструкция 6 используются в новых обычных анализах `analyze_saved`. Контракт 3 и инструкция 5 остаются доступны для исторических примеров и замороженного сравнения medium/high. Базовые правила версии 3 и дополнительная политика версии 2 не переписываются. Платные повторы по прежнему содержимому по-прежнему блокируются независимо от версии контракта.

## Как устранено переписывание цитат

`source_fragments()` разбивает описание на непустые строки. Для каждого фрагмента сохраняются ID, поле источника, начальная и конечная позиции и точный текст. Опечатки не исправляются. Название получает отдельный ID `title`.

Модель получает `description_fragments` вместо дублирования всего описания и выбирает `quote_ids` или `quote_id`. В JSON Schema перечисляются допустимые ID конкретной вакансии. После ответа Python проверяет ID и подставляет исходную строку. Неизвестный ID или лишнее поле с произвольной цитатой отклоняются. Это устраняет ошибки воспроизведения букв, но не гарантирует, что модель выбрала подходящее доказательство: смысловую связь нужно проверять отдельно.

Оригинальный ответ находится в `output_text`; `source_analysis` содержит ответ контракта 4; `source_fragments` — таблицу источников. Совместимое поле `assessment.analysis` содержит представление контракта 3 с цитатами, чтобы прежние отчёты могли его читать. Это программное разрешение ссылок, а не второй ответ модели. Для контракта 4 восстановление пунктуации не применяется.

## Задачи и входная готовность

`main_work.fit` описывает сходство задач. Новое `entry_readiness` описывает готовность работать сейчас, а `readiness_reason` объясняет её. У каждого требования есть `role` (core/supporting), `required_level` (basic/working/advanced/unspecified) и `requires_hearing`.

Неподтверждённое обязательное ключевое требование отправляет карточку в профессиональный разбор `review`, а не в обычный `show`. Если опубликованный уровень ключевого требования высокий, неподтверждённая готовность даёт `unsuitable/review`. Это консервативная сортировка для текущего поиска, не доказательство неспособности. Поле не превращает все неизвестные навыки в отказы: вспомогательное требование остаётся обычным вопросом. Модель должна правильно определить центральность, уровень и обязательность; программа не может гарантировать правильность этих смысловых меток.

`ready` запрещён при ключевых пробелах; `not_ready` требует ключевого пробела либо основной работы другого типа. Несогласованный ответ не маскируется автоматически под верный.

## Слух

Если в evidence прямо указано отсутствие слуха, требование слухового восприятия становится `conflict` независимо от языка. Проверка использует `requires_hearing` и явные формулировки в тексте выделенного требования. Исправление статуса записывается в `semantic_corrections`, исходный ответ не меняется. `preferred` не становится обязательным запретом; `mandatory` даёт `unsuitable/exclude` как недоступное обязательное условие. Само чтение документации и работа с готовыми текстовыми транскриптами слуха не требуют.

Это целевая проверка известных формулировок, а не универсальное понимание всех языков. Если модель не выделит требование или неверно опишет его, ошибка ещё возможна. Новые инструкции усиливают эту часть, но их качество нужно проверить реальными ответами.

## Проверки

Тесты проверяют сохранение исходной опечатки и позиций, отклонение неизвестных ID и произвольных цитат, контраст ключевого и вспомогательного требования, конфликт готовности, обязательный и предпочтительный слух. MockTransport проверяет полный путь запроса и ответа контракта 4 без сети. Исторический пакет medium/high дополнительно проверен локальной сборкой: прежние запросы остались неизменными.

Реальные платные запросы в этом изменении не запускались. Следующая смысловая проверка выполняется новым входом контракта 4; старые неуспешные ответы не превращаются в успешные задним числом.
